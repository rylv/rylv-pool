# CI and release setup

The workflow layout follows [rylv-metrics](https://github.com/rylv/rylv-metrics/tree/master/.github/workflows),
adapted to this crate's fixed-capacity pool and provider-selected entries.
All workflows are source files: adding them does not dispatch a run or publish a crate.

## Checks

| Job | Scope |
| --- | --- |
| Tests | Stable Rust on Linux, macOS, and Windows; debug and release profiles, including benchmark smoke scenarios |
| Clippy | All targets on the three platforms; warnings are errors |
| Formatting | Root crate and the isolated fuzz workspace |
| MSRV | Rust 1.85.0, matching Cargo.toml; checks and tests on all three platforms |
| Documentation | Rustdoc warnings are errors, examples, and compile-fail API contracts |
| Coverage | Instrumented tests, minimum 95% production line coverage, LCOV/HTML/JSON artifacts |
| Miri | Bounded safety scenarios and external providers, strict provenance, three scheduler seeds, cached sysroot |
| Fuzz | Lifecycle state machine, 60 seconds per CI run, cached corpus and crash artifacts |
| Audit | Root and fuzz dependencies against RustSec, also every Monday |
| Deny | License, registry, git-source, and dependency policy for both workspaces |
| Semver | Compare with the latest non-yanked stable crates.io release when compatibility is required |
| Benchmarks | Compare Criterion baselines with critcmp for the PR base and head on the same runner; retain reports |
| CI scripts | Unit tests for benchmark migration detection and the regression gate |

`ci.yml` runs on pull requests, manual dispatch, and pushes to `main`, `master`,
`feature/**`, and `codex/**`. It is also reusable by `release.yml`.
`security.yml` can run independently and performs the scheduled dependency checks.
The crate currently has no feature flags, so separate default/no-default feature
matrices would repeat the same build. Benchmarks run as smoke scenarios under
`cargo test --all-targets`. A separate pull-request job measures optimized
benchmarks on the base and head commits on the same runner and compares their
Criterion results with critcmp. A PR mean batch time increase greater than 15%
fails the job. The gate uses critcmp's threshold filtering and baseline order,
so rounded display ratios do not decide whether a case fails. Added and removed
scenarios are reported separately; a comparison with no common scenarios fails.
The initial migration skips comparison when the base commit still uses the old
harness, recording that reason in the job summary. Once Criterion is on the base
branch, subsequent pull requests are compared automatically. See
[benchmark methodology](benchmarks.md).

## Coverage and safety

Coverage checks require at least 95% of production lines. Inspect uncovered
production paths in the HTML report before changing the threshold or adding tests.
Test helpers, fuzz sources, and benchmark sources are excluded from the production
coverage calculation; production code exercised by any target still contributes.
Doctests run separately; stable coverage instrumentation does not include them.
Coverage exports reuse the same instrumented run rather than running tests again.

Miri tests and fuzzing complement the deterministic unit and integration suite.
They do not exhaustively enumerate all possible lock-free queue interleavings.
Miri's different seeds provide additional schedules and memory-model checks.
The three seed jobs share a sysroot cache keyed by operating system, architecture,
and a fingerprint of the installed nightly compiler. A new nightly gets a new
cache key. `cargo miri setup` runs after restoration to validate the sysroot.
Concurrency tests use synchronization and exact lifecycle counts rather than sleeps.

The fuzz workspace has independent dependencies. Its lockfile is generated by CI
and uploaded as an artifact; it is not committed or frozen with the root crate.
The root Cargo.lock is committed and root cargo commands use `--locked`.
Dependency policies are separate: `deny.toml` applies to the published pool and
`fuzz/deny.toml` applies to the fuzz workspace. Only the latter allows NCSA for
`libfuzzer-sys`. `make deny` and CI check both configurations explicitly.
Dependencies and Actions are kept current with weekly Dependabot updates.
Actions are pinned to full commit hashes.
The installed cargo-fuzz, cargo-llvm-cov, cargo-audit, cargo-deny, and critcmp
versions are also fixed in the workflows; update these deliberately when
upgrading tooling.

## Local commands

`make help` lists the commands. Additional safety tools and benchmarks are opt-in.

```sh
make verify
make test-release
make bench
make bench BENCH_ARGS='warm/ --sample-size 50 --measurement-time 3'
make ci-scripts
make msrv
make coverage
make miri MIRI_SEED=1
make fuzz FUZZ_SECONDS=300
make audit
make deny
```

Optional tooling must be installed before those targets are used:

```sh
rustup toolchain install 1.85.0 --profile minimal
rustup component add llvm-tools-preview
rustup toolchain install nightly --component miri
cargo install cargo-llvm-cov --version 0.8.4 --locked
cargo install cargo-fuzz --version 0.13.1 --locked
cargo install cargo-audit --version 0.22.2 --locked
cargo install cargo-deny --version 0.20.2 --locked
cargo install critcmp --version 0.1.8 --locked
```

## GitHub configuration

1. Confirm that the repository URL in Cargo.toml matches the GitHub repository
   before publishing.
2. Enable GitHub Actions and protect the default branch with required CI jobs.
   Prefer the complete CI set, including safety and coverage jobs, rather than
   only unit tests.
3. Create the `crates-io` environment. Configure any desired reviewer protection
   and an environment secret named `CARGO_REGISTRY_TOKEN` with permission to
   publish `rylv-pool`.
4. Allow the release job to create GitHub releases. Its `contents: write`
   permission is scoped to that job; other jobs use read access.

Pull-request checks do not use registry secrets. The first publication skips the
semver baseline check when crates.io returns 404. Subsequent compatible releases
are compared against the published API. A major version increase, or a minor
increase while the major version is zero, permits breaking changes.
Network failures and authorization errors do not silently disable compatibility
checks.

## Release procedure

Update Cargo.toml and add nonempty notes under `## [X.Y.Z]` in CHANGELOG.md.
Run the desired local checks and commit the release files. Pushing a tag `vX.Y.Z`
starts the release workflow; no tags are created by this setup.

CI and Release use distinct concurrency groups so the called CI does not wait
on the release that invoked it. The release runs the complete reusable CI,
verifies that the tag equals the
manifest version, and performs `cargo publish --dry-run`. Only then does it
publish through the `crates-io` environment. The GitHub release is created after
successful crates.io publication and uses the matching changelog section.
If publication succeeds but GitHub release creation fails, rerun only the failed
release job; publishing the same crate version again is not supported by crates.io.
